PawnLoan support runbook

Girvi and Loans operate independently during coexistence. Service each loan in the application that owns it; never move or dual-write records between them.

Scheduled risk reassessment

Run the bounded tenant command daily after the workspace's rates and prior-day accounting work are available. Replace TENANT_SCHEMA and WORKSPACE_ID with the values for the same workspace:

python manage.py tenant_command reassess_pawn_loans --schema=TENANT_SCHEMA --workspace-id=WORKSPACE_ID --batch-size=100

For a controlled business date, add --as-of=YYYY-MM-DD. Without it, the command uses the application server's current date. Batch size must be between 1 and 1,000.

  1. Schedule one invocation per tenant workspace. The schema and workspace ID must identify the same workspace or the command fails closed.
  2. Repeat the command until it reports selected=0 when a workspace can have more active loans than the chosen batch size.
  3. Treat a non-zero process exit as a monitoring alert. Successful loans remain refreshed; failed loans retain an Error snapshot with the specific blocker.
  4. Open the Risk portfolio to review Error or Stale rows. Correct policy, appraisal, valuation-rate, schedule, or accounting evidence rather than editing a snapshot.
  5. Confirm the Operations Console shows zero unassessed active loans and a recent last risk assessment.

Result fields: selected is the claimed due work, current is successfully refreshed work, and errors is failed work requiring review. Re-running is safe: current snapshots for the same or later assessment date are skipped, while stale and error rows are retried.

Failed accounting delivery

  1. Open the reconciliation report and confirm the source event/outbox payloads agree.
  2. Correct the displayed DEA period, ledger, or Party-account setup blocker.
  3. Use Queue retry once. Never create a voucher or journal manually.
  4. Confirm the event becomes Posted and its DEA references reconcile.

Sequence or license blocker

  1. Open the linked license setup.
  2. Expired/inactive licenses remain attached to existing loans but cannot issue new loans.
  3. If a sequence is exhausted, create or select a new active series; never reset or reuse committed numbers.
  4. Both pawn-loan and release sequences must be ready.

Reversal and custody problem

  1. Use the reconciliation report to identify the newest unreversed dependent event.
  2. Reverse events strictly newest-first with an administrator reason.
  3. Never edit posted DEA records, immutable releases, accruals, or custody history.
  4. If physical custody differs from the system, stop servicing and escalate; do not force a reversal.

Deployment and rollback

Tenant migrations must use migrate_schemas. Before enablement, run migrations, checks, the E5.5 end-to-end suite, and reconciliation. Rollback means disable future Loans navigation/creation and redeploy the previous compatible code; never delete Loans records or mutate posted accounting. Existing new-app loans remain owned by Loans and must still be serviced there.

The detailed command and verification checklist is maintained in docs/implementation/pawn-loan-mvp-operations-runbook.md.
