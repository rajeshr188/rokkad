# Girvi Number Sequence Migration Plan

## Goal

Move Girvi document ID generation from scan-based allocation to locked sequence-row allocation while keeping the domain relationship:

```text
License -> Series -> GivenLoan / TakenLoan / Release
```

The target design keeps `Series` as the business and compliance bucket, and introduces sequence rows for document-specific numbering:

```text
Series -> GirviNumberSequence(document_kind, prefix, width, next_number)
```

## Non-Goals

- Do not remove `Series`.
- Do not renumber existing loans or releases.
- Do not reuse old missing numbers automatically.
- Do not change DEA voucher numbering.
- Do not make releases or taken-loan settlements post accounting directly; posting remains through existing DEA boundaries.

## Target Model Shape

Add a tenant app model, naming can be finalized during implementation:

```text
GirviNumberSequence
- series -> Series
- document_kind
- prefix
- width
- next_number
- is_active
- last_allocated_number
- last_allocated_at
- created_at
- updated_at
- updated_by
- notes
```

Uniqueness:

```text
unique(series, document_kind)
```

Initial `document_kind` values:

```text
GIVEN_LOAN
TAKEN_LOAN
GIVEN_LOAN_RELEASE
TAKEN_LOAN_SETTLEMENT
```

`TAKEN_LOAN_SETTLEMENT` should be used instead of `TAKEN_LOAN_RELEASE` unless a later domain decision creates a true release document for taken loans.

## Series Responsibility After Migration

`Series` remains the business/register/control object and keeps:

- `license`
- `name`
- `loan_type` for compatibility until retired or softened
- `is_active`
- guardrail thresholds
- deactivation rule/status fields
- reporting helpers

Long-term, these fields move from `Series` to `GirviNumberSequence`:

- `prefix`
- `max_limit`

During migration, keep them as compatibility/display fields until all forms, templates, imports, and services read from `GirviNumberSequence`.

## Allocation Policy

Generated numbers are monotonic per `(series, document_kind)`.

Allocation:

1. Resolve `series`.
2. Resolve `document_kind`.
3. Open a transaction.
4. Lock `GirviNumberSequence` with `select_for_update()`.
5. Read `next_number`.
6. Format `prefix + padded(next_number, width)`.
7. Increment `next_number`.
8. Save the target document with the generated ID.

Preview:

- Preview reads the sequence but does not increment it.
- Preview is advisory only. It must tolerate a different number at save time if another user creates a document first.

Manual legacy entry:

- Allow explicit manual IDs during import/manual migration workflows.
- Validate uniqueness across relevant runtime tables.
- After manual entry/import, sync the sequence to `max(existing numeric suffix) + 1` for the matching `(series, document_kind)`.

Delete behavior:

- Deleting a saved draft does not rewind by default.
- Admin-only rewind may be allowed only for the last unused draft number and only when there are no side effects: no payment, voucher, journal, release, renewal, custody, statement, notice, print, or external reference.
- Older gaps must not be auto-filled.

## Phase 0: Decision And Inventory

Status: planning.

Tasks:

1. Confirm all document identifiers currently generated by Girvi:
   - `GivenLoan.loan_id`
   - `TakenLoan.loan_id`
   - `Release.release_id`
   - any taken-loan settlement/return document identifier if introduced
2. Inventory all reads/writes of:
   - `Series.prefix`
   - `Series.max_limit`
   - `Series.get_next_loan_id()`
   - `Series.format_loan_id()`
   - `LoanIDGenerator`
   - `ReleaseIDGenerator`
3. Confirm UI surfaces that preview next IDs:
   - create loan form
   - series next-loan-id endpoint
   - release form, if any
4. Confirm import/manual-entry paths that need explicit ID support.

Exit criteria:

- Inventory is complete.
- No runtime behavior changed.

## Phase 1: Add Sequence Model And Read-Only Helpers

Tasks:

1. Add `GirviNumberSequence` model.
2. Add a tenant migration.
3. Add a selector/helper to find or preview sequence values without allocation.
4. Add tests for:
   - one row per `(series, document_kind)`
   - preview does not increment
   - inactive/missing sequence behavior is fail-closed with actionable errors

Tenant migration rule:

- Use `migrate_schemas` for tenant rollout.

Exit criteria:

- Model exists.
- No production workflow uses it for allocation yet.

## Phase 2: Backfill Sequences From Existing Data

Tasks:

1. Backfill sequence rows for each existing `Series`.
2. For each series and document kind, compute next number from existing documents:
   - parse IDs matching the sequence prefix
   - ignore non-matching legacy IDs but report them
   - set `next_number = highest parsed suffix + 1`
3. Seed defaults from current `Series.prefix` and `Series.max_limit`:
   - `GIVEN_LOAN`: current series prefix/width for given series
   - `TAKEN_LOAN`: current series prefix/width for taken series, or configured default
   - `GIVEN_LOAN_RELEASE`: release prefix default, then allow admin correction
   - `TAKEN_LOAN_SETTLEMENT`: settlement prefix default, then allow admin correction
4. Add a dry-run management command before any apply mode.
5. Record non-matching/manual ID warnings for user review.

Exit criteria:

- Dry run reports expected sequence rows.
- Apply mode creates rows idempotently.
- Running apply twice does not change already-correct rows unexpectedly.

## Phase 3: Allocation Service

Tasks:

1. Introduce a dedicated allocation service, for example:

```text
GirviNumberSequenceService.preview(series, document_kind)
GirviNumberSequenceService.allocate(series, document_kind)
GirviNumberSequenceService.sync_from_existing(series, document_kind)
```

2. Use row locks for allocation.
3. Keep formatting logic inside the sequence service.
4. Keep manual ID validation separate from generated allocation.
5. Add tests for:
   - allocation increments once
   - preview does not increment
   - allocation is scoped by document kind
   - generated IDs do not collide with existing manual IDs
   - errors are actionable when sequence setup is missing

Exit criteria:

- Service is covered by focused unit tests.
- Existing `LoanIDGenerator` and `ReleaseIDGenerator` remain compatibility callers.

## Phase 4: Switch GivenLoan And TakenLoan Generation

Tasks:

1. Route `LoanIDGenerator.generate()` through `GirviNumberSequenceService.allocate()`.
2. Determine `document_kind` from concrete model or explicit caller:
   - `GivenLoan` -> `GIVEN_LOAN`
   - `TakenLoan` -> `TAKEN_LOAN`
3. Update create-preview paths to use sequence preview, not allocation.
4. Keep manual `loan_id` support for imports and controlled manual entry.
5. Add regression tests for:
   - GivenLoan auto ID
   - TakenLoan auto ID
   - preview without increment
   - manual legacy ID entry
   - cross-table duplicate blocking
   - missing sequence setup message

Exit criteria:

- New GivenLoan/TakenLoan IDs allocate through sequence rows.
- Existing public behavior and form fields remain compatible.

## Phase 5: Switch Release Numbering

Tasks:

1. Route `ReleaseIDGenerator.generate()` through sequence allocation.
2. Use the loan's `series` and `GIVEN_LOAN_RELEASE`.
3. Preserve manual/imported release IDs if any current workflow allows them.
4. Add tests for:
   - release ID allocation under loan series
   - release preview if surfaced
   - release creation rollback does not partially save the release
   - sequence gaps are accepted
   - no accidental loan sequence consumption

Exit criteria:

- Release IDs allocate from `GIVEN_LOAN_RELEASE`.
- GivenLoan IDs and release IDs do not share a sequence.

## Phase 6: TakenLoan Settlement Numbering

Tasks:

1. Decide the target source document for taken-loan settlement/collateral return.
2. If a persisted settlement/return document exists or is introduced, allocate IDs from `TAKEN_LOAN_SETTLEMENT`.
3. If no first-class document exists yet, keep the sequence row seeded but unused.
4. Add tests only when runtime settlement document allocation exists.

Exit criteria:

- No pretend release concept is introduced for TakenLoan.
- Numbering waits for a real source-document workflow.

## Phase 7: Admin/UI Controls

Tasks:

1. Add a sequence management surface under Girvi series/license settings.
2. Allow guarded edits:
   - prefix
   - width
   - next_number
   - active flag
3. Validation:
   - lowering `next_number` below existing max is blocked by default
   - force changes require explicit admin action and audit note
   - prefix/width changes preview the next generated value
4. Add audit logging for edits.
5. Expose sync action:
   - dry run first
   - apply only with Owner/Admin permission

Exit criteria:

- Users can correct sequence setup safely after legacy entry/import.
- Sequence edits are auditable.

## Phase 8: Compatibility Retirement

Tasks:

1. Remove direct generation dependence on `Series.prefix` and `Series.max_limit`.
2. Update templates/docs to describe sequences as the numbering source.
3. Decide whether to:
   - remove `Series.prefix` and `Series.max_limit`, or
   - keep them as display/default fields only
4. Remove stale helper paths only after import, release, loan create, and repledge creation tests prove sequence allocation is stable.

Exit criteria:

- `GirviNumberSequence` is the only runtime source of generated IDs.
- Remaining Series fields are either removed or explicitly compatibility-only.

## Risks

1. Bad backfill can set `next_number` too low and create collisions.
2. Prefix changes can make old/manual IDs hard to parse.
3. Preview users may expect the previewed ID to be guaranteed.
4. Deleting drafts and reusing numbers can create audit confusion.
5. TakenLoan settlement numbering can become premature if no source document exists.

## Guardrails

1. Never renumber existing documents.
2. Never auto-fill old gaps.
3. Do not rewind on delete by default.
4. Preview does not allocate.
5. Allocation must be transactionally locked.
6. Manual IDs must be uniqueness-checked.
7. Sequence sync must be dry-run capable.
8. Tenant rollout uses `migrate_schemas`.
