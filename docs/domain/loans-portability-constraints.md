# Loans constraints and applicability

Read with [the audit](../architecture/loans-portability-audit.md) and the
[complete declared field/constraint inventory](../implementation/loans-portability-schema-inventory.md).
This inventory classifies important semantic rules; the generated companion lists
all 170 named model constraint declarations and every declared field in the two
apps. Constraints generated by migrations/triggers and rules in commands are
listed here separately. It is a source audit, not introspection of deployed SQL.

## Classification and enforcement vocabulary

- A: fundamental domain/truth/isolation invariant.
- B: native operational workflow rule.
- C: structural database integrity.
- D: current product policy or supported implementation bound.
- E: derived value or consistency relation.
- F: historical evidence expectation that may be unavailable.
- G: presentation/input requirement.
- H: import/restore requirement.

Multiple categories are intentional: a rule can be structural for an admitted
operational row without being fundamental to all historical evidence.
“Stage” means capture/validate before review; “commit” means recheck under current
authority and relevant locks. No rule below authorizes direct invalid writes.
Retaining a contradictory source assertion is not violating an operational SQL
constraint: it belongs to a different representation.

required for operational admission; E = preserve as source evidence, not enforce
as a prerequisite to historical acceptance; — = not relevant. “Re-import” means

## Duplication and workflow-to-persistence findings

The disbursal snapshot FK graph encodes an approval workflow. Custody events require
one recognized operational source. The PawnLoan schema requires known positive
tenure and structured collateral supports calculations with non-null net/purity.
Those are legitimate operational structures but unsuitable as the only historical
representation. The cleanest correction is a boundary, not disabling those checks.

Model checks, pure-domain validation, command validation and SQL reference/immutability
guards overlap deliberately. Do not remove repeated checks without identifying
which caller or bypass path each protects. Accidental duplication includes multiple
opening-origin checks with separately phrased capability errors, model-derived
restore validation, and repeated setup/identity resolution across import/export.
Current safety still depends on these checks until a replacement boundary is tested.

The ordinary transition dictionary is not a database check on `PawnLoan.state`.
Likewise a Django `choices` value or model `clean()` call is not universally a SQL
constraint. Generated inventory rows describe declarations; migration guards and
actual command paths determine enforcement. This distinction explains why tightening
an importer and protecting evidence tables do not automatically secure the legacy
generic aggregate writer.
